# FIIO Air Link Control Roadmap

## Текущий статус

- Этап 0: реализация завершена. Добавлены build version/commit, capability baseline
  и аппаратный smoke-test. GET-проверка и codec write/readback пройдены на firmware
  `1.4.0`; проверка EXE на отдельной чистой Windows-системе остаётся release-задачей.
- Этап 1: реализация завершена. Добавлены lifecycle state machine, auto-connect,
  обнаружение физического disconnect, reconnect, ручное отключение и BDUI polling.
  Автоподключение проверено на реальном устройстве; сценарий физического извлечения
  и повторного подключения USB остаётся ручным hardware smoke-test.
- Этап 2: завершён. Добавлены HID/build summary, transport и lifecycle metrics,
  время последнего ответа, ограниченный development packet log, BDUI tabs/table/copy
  и экспорт JSON с полным редактированием payload.
- Этап 3: завершён. Кодеки настраиваются напрямую отдельными переключателями;
  применение выполняется одной явной командой с обязательным codec readback.
  Пресеты намеренно отсутствуют, чтобы не дублировать это управление и не
  загромождать интерфейс.
- Этап 4: завершён. LDAC и aptX Adaptive SET-команды аппаратно проверены с
  восстановлением исходных значений. Добавлены firmware-gated controls и
  обязательный property-specific readback.
- Этап 5: завершён. Connect `16` и disconnect `17` аппаратно проверены. Action
  отправляется один раз, после чего состояние подтверждается GET polling списка
  сопряжённых устройств и connection status.
- Этап 6: завершён. Все HID reads выполняет один
  background reader, report `9` и unmatched report `8` изолированы от command
  responses, события проходят debounce и запускают refresh состояния. Core
  handshake commands `8/7` payload `24` аппаратно подтверждены; discovery `0x81`
  и state events `0x83/0x84/0x85` получены и декодированы.
- Этап 7: discovery UI и pair action реализованы. Manual pairing restart `0 → 2`
  аппаратно подтверждён, найденные устройства отображаются из event `0x81`,
  command `18` отправляется только по выбранному свежему адресу и проверяется
  event `0x83`/command `14`. Discovery entries и pair attempt используют отдельные
  15-секундные deadlines, как FIIO Control.
- Выход из manual search выполняется через стабильный mode `1`; mode `0`
  используется только как промежуточный reset и не проходит устойчивый readback.
- Успешный pair action `18`, event `0x83` и paired-device list readback аппаратно
  подтверждены; pairing доступен без firmware-gating.
- CI собирает portable Windows EXE, создаёт SHA-256 и загружает оба файла как
  artifact; подпись и installer остаются release-задачами.
- Следующий этап: исследовать удаление одного сопряжения.

## Принципы разработки

- Каждую новую SET-команду сначала исследовать отдельно на реальном устройстве.
- После SET выполнять targeted readback только изменённого свойства.
- Не считать операцию успешной до подтверждения фактического состояния.
- Не выполнять автоматические retry для записывающих и разрушительных команд.
- Не позволять notifications завершать активные запросы транспорта.
- Не добавлять Air Link-специфичную логику в универсальный BDUI renderer.
- Не реализовывать firmware update без полного протокола обновления и восстановления.

## Этап 0. Стабильная основа

**Цель:** зафиксировать рабочую версию перед расширением протокола.

Задачи:

1. Зафиксировать текущую BDUI-архитектуру и HID transport.
2. Проверить portable EXE на чистой Windows-системе.
3. Добавить версию приложения и commit hash в диагностический экран.
4. Описать подтверждённые возможности firmware `1.4.0`.
5. Создать аппаратный smoke-test:
   - подключение;
   - чтение firmware;
   - чтение кодеков;
   - чтение соединения;
   - чтение списка устройств;
   - изменение кодеков с readback;
   - отключение USB во время GET.

**Критерий готовности:** unit-тесты и аппаратный smoke-test проходят, EXE запускается без установленного Python.

## Этап 1. Жизненный цикл подключения

**Цель:** приложение самостоятельно реагирует на USB-подключение и отключение.

Задачи:

- Ввести состояния `offline`, `searching`, `connecting`, `synchronizing`, `connected`, `reconnecting`, `error`.
- Добавить периодическое обнаружение Air Link.
- Автоматически подключаться при появлении устройства.
- Обрабатывать физическое отключение без зависших команд.
- Отменять результаты устаревшей сессии после reconnect.
- Добавить ручную кнопку отключения сессии.
- Показывать прогресс подключения через BDUI.

Основные файлы:

- `fiiocontrol/hid_backend.py`: отслеживание HID-интерфейсов.
- `fiiocontrol/controller.py`: state machine подключения.
- `fiiocontrol/app.py`: новые actions.
- `fiiocontrol/ui_document.py`: экраны состояний.
- `fiiocontrol/transport.py`: завершение активного запроса.

Тесты:

- подключение найденного интерфейса;
- отсутствие устройства;
- disconnect во время команды;
- reconnect;
- защита от параллельных подключений;
- игнорирование результата старой сессии.

**Критерий готовности:** устройство можно извлечь и подключить обратно без перезапуска приложения.

## Этап 2. Диагностика и наблюдаемость

**Цель:** упростить исследование неподтверждённых команд.

Функции:

- Диагностический BDUI-экран.
- Отображение VID/PID, HID path, usage page, usage, report IDs и firmware.
- Время последнего успешного обмена.
- Счётчики timeout, disconnect и reconnect.
- Development packet logger.
- Разделение пакетов на requests, responses, notifications и malformed packets.
- Экспорт диагностического JSON.
- Маскирование Bluetooth-адресов при экспорте.
- Ограниченный кольцевой буфер пакетов.

BDUI-компоненты:

- `tabs`;
- `table`;
- `copy`;
- `download`.

**Критерий готовности:** неизвестный HID-пакет можно безопасно записать и проанализировать без изменения устройства.

## Этап 3. Прямая настройка кодеков

**Цель:** управлять разрешёнными кодеками устройства без промежуточных профилей.

Поведение:

1. Прочитать фактически включённые кодеки с устройства.
2. Показать отдельный переключатель для каждого поддерживаемого кодека.
3. Активировать кнопку применения только после изменения конфигурации.
4. Выполнить codec SET по явному действию пользователя.
5. Прочитать кодеки обратно.
6. Сообщить успех только при полном совпадении.
7. Сохранить последнее подтверждённое состояние при ошибке.

Ограничения:

- Локальные пресеты отсутствуют.
- UI не подменяет состояние устройства сохранёнными значениями.
- Фактически согласованный кодек соединения может отличаться от разрешённого набора.

**Критерий готовности:** пользователь напрямую включает и выключает кодеки, а каждое изменение подтверждается readback.

## Этап 4. Управление LDAC и aptX Adaptive

**Цель:** добавить подтверждённое управление качеством.

Команды:

- aptX GET `64`, SET `65`.
- LDAC GET `66`, SET `67`.

Порядок аппаратной проверки:

1. Считать исходное значение.
2. Записать одно допустимое значение.
3. Подождать минимум 300-500 мс.
4. Выполнить целевой GET.
5. Вернуть исходное значение.
6. Записать фактические пакеты и результат.

Ограничения:

- aptX mode доступен только при включённом aptX Adaptive.
- LDAC mode доступен только при включённом LDAC.
- SET-команды не получают автоматических retry.
- Выбранный режим не считается реально согласованным кодеком соединения.

Реализация:

- Добавить `set_aptx_mode()` и `set_ldac_mode()` в `device.py`.
- Добавить обязательный property-specific readback.
- Ввести capability flags для firmware.
- Добавить BDUI `select` или segmented control.
- Откатывать UI при несовпадении readback.

**Критерий готовности:** каждый режим аппаратно проверен, восстанавливается после ошибки и покрыт тестами.

Статус: завершено для firmware `1.4.0`. LDAC проверен последовательностью
`1 → 2 → 1`, aptX Adaptive — `19 → 3 → 19`; исходный codec set восстановлен.

## Этап 5. Connect и disconnect сопряжённых устройств

**Цель:** управлять существующими сопряжениями.

Команды:

- Connect: `16`.
- Disconnect: `17`.
- Payload: `0, ...Bluetooth address, 0`.

Порядок операции:

1. Показать выбранное устройство.
2. Отправить action.
3. Дождаться settle delay.
4. Прочитать connection status и paired-device list.
5. Подтвердить изменение по readback.
6. При timeout оставить состояние неопределённым и предложить refresh.

BDUI:

- Action-кнопка возле каждого устройства.
- Busy-состояние только выбранной строки.
- Статусы `connecting` и `disconnecting`.
- Защита от двойного запуска.

**Критерий готовности:** известный приёмник подключается и отключается без перезапуска приложения.

Статус: завершено для firmware `1.4.0`. Disconnect подтверждён переходом target
в `connected=false`, connect восстановил `connected=true` и headset count `1`.

## Этап 6. Notifications

**Цель:** получать изменения без полного ручного refresh.

Исследование:

- Декодировать input reports `8` и `9`.
- Проверить notification registration.
- Снять пакеты при подключении и отключении приёмника.
- Снять пакеты при начале и завершении pairing.
- Снять пакеты при изменении кодека.

Транспорт:

- Requests остаются строго последовательными.
- Ответы сопоставляются по feature и command.
- Несопоставленные пакеты отправляются notification dispatcher.
- Notifications не могут завершать активный request.
- Неизвестные события сохраняются только в debug-буфере.

Контроллер:

- Обновляет отдельные поля состояния.
- Выполняет debounce повторяющихся событий.
- Запускает полный refresh только при неизвестном или противоречивом событии.

**Критерий готовности:** подключение и отключение приёмника отражается в UI автоматически и не ломает активные команды.

## Этап 7. Поиск и pairing

**Цель:** сопрягать новые Bluetooth-приёмники.

Состояния:

- `idle`;
- `starting`;
- `scanning`;
- `device_found`;
- `pairing`;
- `paired`;
- `connecting`;
- `failed`;
- `cancelled`.

Функции:

- Включение ручного pairing mode.
- Отображение найденных устройств.
- Отдельные списки paired и discovered.
- Pair action `18`.
- Отмена сканирования.
- Timeout pairing.
- Автоматическое обновление списка после успеха.

**Условие начала:** этап выполняется только после декодирования notifications.

**Критерий готовности:** новый приёмник можно найти, сопрячь и подключить через одну управляемую state machine.

## Этап 8. Безопасное удаление сопряжения

**Цель:** удалять одно устройство без риска массового сброса.

Функции:

- Delete one: command `19`.
- Диалог с именем и Bluetooth-адресом.
- Явное подтверждение.
- Отсутствие automatic retry.
- Readback списка после удаления.
- Блокировка удаления подключённого устройства либо предварительный disconnect.

Пока не реализовывать:

- delete all;
- factory reset;
- reboot;
- firmware update.

**Критерий готовности:** удаляется только выбранное устройство, результат подтверждается новым списком.

## Этап 9. Формализация BDUI

**Цель:** сделать UI-схему расширяемой и проверяемой.

Задачи:

- JSON Schema для `fiiocontrol.bdui/v1`.
- Валидация документа перед отправкой renderer.
- Компоненты `dialog`, `toast`, `progress`, `tabs`, `select`, `table`, `confirm-action`, `empty-state`.
- Capability-driven rendering.
- Версионирование actions.
- Запрет неизвестных actions на backend.
- Snapshot-тесты документов.
- Обработка несовместимой версии schema.

**Критерий готовности:** новая функция добавляется через document builder без специальной Air Link-логики в JavaScript renderer.

## Этап 10. Релизная инфраструктура

**Цель:** подготовить приложение к обычному использованию.

Задачи:

- Подписанный EXE.
- Installer с ярлыком и удалением.
- Версия приложения в интерфейсе.
- Автоматическая CI-сборка Windows artifact.
- Unit-тесты и BDUI schema validation в CI.
- Hardware release checklist.
- Проверка обновлений без автоматической установки.
- Опциональный автозапуск.
- Системный tray после стабилизации reconnect.

**Критерий готовности:** воспроизводимая подписанная сборка создаётся CI и проходит release checklist.
